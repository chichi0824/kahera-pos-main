    DATABASE GUIDE · OWNER / ADMIN REFERENCE

    Operating the live Kahera database

    This guide covers the shared Cloudflare D1 database used by the POS and customer ordering page: how to inspect records, make a backup, apply reviewed database changes, and handle common live operations.

    Live database warning: commands marked REMOTE affect the shared business database used by every cashier device and the customer ordering page. Do not experiment, reset data, or run unfamiliar SQL against it. Export a backup first and verify the target database before any change.

    Modified by Maryjoy Tan (MJ)

    1. Understand how Kahera stores data

    • Cloudflare D1: the shared database named kahera-db, connected to the Worker through the kahera_db binding. The configured primary location is APAC.
    • Shared across devices: menu categories, menu items, prices, availability, sold-out status, menu photos, store settings, orders, order items, payment details, and daily report / shift records.
    • Customer orders: online orders are saved in the same orders and order_items tables. They begin as unpaid; the cashier marks them paid after receiving payment.
    • Device-local data: an in-progress register cart and the browser's acknowledged-order reminder state are not shared D1 records. Do not expect another cashier device to see an unfinished cart.
    • Daily reports: one report/shift record is maintained per Manila calendar date. The Worker has a scheduled trigger that runs every minute to maintain daily report rollover.

    D1 stores amounts as integer centavos. For example, ₱125.00 is stored as 12500. Do not manually convert or edit amounts without understanding the affected fields.

    2. Open the Worker project and verify the target

    Open Terminal and move to the Worker folder:

    cd ~/kahera-pos-main/cloudflare-worker

    Check wrangler.toml. The database configuration should identify:

    name = "kahera-menu-api"
binding = "kahera_db"
database_name = "kahera-db"
database_id = "96b04312-003f-49e9-a5e4-1646babb4a53"

    Check the database information before proceeding:

    npx wrangler d1 info kahera-db

    Use the exact project folder and database name above. If the name or ID does not match, stop and confirm the configuration before running any remote command.

    3. Make a manual backup before changes

    Export the complete remote database (schema and data) to a timestamped SQL file:

    npx wrangler d1 export kahera-db --remote --output=./kahera-db-backup-before-change.sql

    Keep the backup in a safe location outside the public website folder and repository. Do not commit customer names, phone numbers, delivery addresses, payment references, or payment proof photos to GitHub.

    For a quick count-only check, run:

    npx wrangler d1 execute kahera-db --remote --command="SELECT 'orders' AS table_name, COUNT(*) AS total FROM orders UNION ALL SELECT 'order_items', COUNT(*) FROM order_items UNION ALL SELECT 'shifts', COUNT(*) FROM shifts UNION ALL SELECT 'menu_items', COUNT(*) FROM menu_items UNION ALL SELECT 'menu_categories', COUNT(*) FROM menu_categories;"

    A successful export is a file you can retain. A row count is not a backup. Protect backup files because they contain business and customer information.

    4. Inspect live records safely (read-only)

    Check recent orders:

    npx wrangler d1 execute kahera-db --remote --command="SELECT order_no, created_at, source, status, payment_method, tendered, change_amount FROM orders ORDER BY created_at DESC LIMIT 20;"

    Check online orders that are still awaiting payment:

    npx wrangler d1 execute kahera-db --remote --command="SELECT order_no, created_at, customer_name, customer_phone, fulfillment_type, status FROM orders WHERE source = 'online' AND status = 'unpaid' ORDER BY created_at DESC;"

    Check daily reports:

    npx wrangler d1 execute kahera-db --remote --command="SELECT report_date, status, started_at, ended_at, close_reason FROM shifts ORDER BY report_date DESC LIMIT 30;"

    Check the current receipt counter:

    npx wrangler d1 execute kahera-db --remote --command="SELECT value AS last_receipt_number FROM order_counters WHERE id = 1;"

    Check applied migrations:

    npx wrangler d1 migrations list kahera-db --remote

    These SELECT commands only read data. Avoid copying customer details into chat, screenshots, or public issue trackers.

    5. Apply a database migration

    Database structure changes must be added as a new, numbered SQL file inside cloudflare-worker/migrations/. Do not edit an older migration that has already been applied to the remote database.

    1. Create the migration in a development branch and review the SQL.
    2. Test it against a local D1 database first.
    3. Review the GitHub pull request. Confirm exactly which tables and records the migration changes.
    4. Export a fresh remote backup and confirm the output file exists.
    5. Check which migrations are pending on the remote database.
    6. Only after approval, apply the pending migration(s) to remote D1.

    List pending remote migrations:

    npx wrangler d1 migrations list kahera-db --remote

    Apply pending migrations (production change):

    npx wrangler d1 migrations apply kahera-db --remote

    Verify afterward:

    npx wrangler d1 migrations list kahera-db --remote

    Do not run migrations apply just to check the database. It changes the remote schema when unapplied migrations exist. Review the proposed migration names and SQL before confirming.

    6. Deploying the Worker is separate from changing the database

    Deploying the Worker publishes API code. Applying D1 migrations changes database structure/data. One does not automatically replace the other.

    From the Worker folder, the Worker deployment command is:

    npx wrangler deploy

    Only deploy after the code has been reviewed and the required database migrations have been applied in the correct order. Confirm the Worker name and environment before deployment.

    The POS website is published separately through GitHub Pages. A website update does not, by itself, deploy the Cloudflare Worker or apply D1 migrations.

    7. If a specific test order must be removed

    Do this only when the order is confirmed to be test data and the owner has approved deletion. First look up the receipt number:

    npx wrangler d1 execute kahera-db --remote --command="SELECT id, order_no, created_at, source, status FROM orders WHERE order_no = 'K-0016';"

    Copy the exact database id, then verify that it identifies the intended test order:

    npx wrangler d1 execute kahera-db --remote --command="SELECT id, order_no, created_at, source, status FROM orders WHERE id = 'PASTE_EXACT_ORDER_ID_HERE';"

    Only after confirming the record and taking a backup, delete its child item rows first and then the order:

    npx wrangler d1 execute kahera-db --remote --command="DELETE FROM order_items WHERE order_id = 'PASTE_EXACT_ORDER_ID_HERE'; DELETE FROM orders WHERE id = 'PASTE_EXACT_ORDER_ID_HERE';"

    Verify that the order no longer exists:

    npx wrangler d1 execute kahera-db --remote --command="SELECT id, order_no FROM orders WHERE id = 'PASTE_EXACT_ORDER_ID_HERE';"

    Receipt numbers (for example, K-0016) are not database IDs. This deletion removes the selected order from every device and affects historical reporting. Never delete a real sale to correct a mistake; use the POS's available order controls and preserve the audit trail.

    8. One-time pre-live reset (test data only)

    Before the first real business day, you may clear the test transactions and test shift/report history so the live system starts with clean sales records. This is a deliberate, irreversible production-data operation. Do not use it after real transactions have started.

    What this reset clears:

    • All order line items in order_items.
    • All POS and online orders in orders, including unpaid online orders and attached payment proof.
    • All cashier shifts and daily report records in shifts.

    What it keeps:

    • Menu categories, menu items, prices, price options, availability, sold-out flags, and menu photos.
    • Store/business profile settings, customer ordering setting, and owner/admin credentials.
    • Database schema and migration history.

    The reset does not delete browser-local carts or locally acknowledged order reminders. Clear browser/site data separately only if you intentionally want to reset a particular device.

    Before you run anything:

    1. Choose a maintenance window when all cashiers are logged out and no one is taking customer orders.
    2. Temporarily disable customer ordering in POS Settings and stop using all cashier devices. Confirm there are no new incoming orders.
    3. Export a full remote backup and keep it somewhere private outside the repository.
    4. Inspect the remote database name/ID and count the records. Confirm every order and shift is test data and that the owner approves clearing it.
    5. If any real sale, customer order, or report exists, do not run this reset. Stop and ask for a selective cleanup plan instead.

    Inspect the data first:

    npx wrangler d1 execute kahera-db --remote --command="SELECT source, status, COUNT(*) AS total FROM orders GROUP BY source, status;"
npx wrangler d1 execute kahera-db --remote --command="SELECT COUNT(*) AS order_items FROM order_items;"
npx wrangler d1 execute kahera-db --remote --command="SELECT COUNT(*) AS shifts FROM shifts;"
npx wrangler d1 execute kahera-db --remote --command="SELECT value AS last_receipt_number FROM order_counters WHERE id = 1;"

    After backup and approval, clear the records in this exact order:

    npx wrangler d1 execute kahera-db --remote --command="DELETE FROM order_items;"
npx wrangler d1 execute kahera-db --remote --command="DELETE FROM orders;"
npx wrangler d1 execute kahera-db --remote --command="DELETE FROM shifts;"

    Deleting child order items first avoids leaving orphaned line items. Orders are deleted before shifts because orders can reference a shift.

    Optional: restart receipt numbering at 1. Do this only if the owner explicitly wants a fresh receipt sequence and all test orders have been removed:

    npx wrangler d1 execute kahera-db --remote --command="UPDATE order_counters SET value = 0 WHERE id = 1;"

    Then verify that the transaction tables are empty:

    npx wrangler d1 execute kahera-db --remote --command="SELECT COUNT(*) AS orders_remaining FROM orders;"
npx wrangler d1 execute kahera-db --remote --command="SELECT COUNT(*) AS order_items_remaining FROM order_items;"
npx wrangler d1 execute kahera-db --remote --command="SELECT COUNT(*) AS shifts_remaining FROM shifts;"
npx wrangler d1 execute kahera-db --remote --command="SELECT value AS last_receipt_number FROM order_counters WHERE id = 1;"

    Confirm the menu, prices, store profile, owner login, and customer ordering configuration are still correct. Re-enable customer ordering only when the business is ready to go live.

    Never run a blanket reset on a live database. Do not delete the database, drop tables, remove migrations, or clear menu/settings tables as part of this procedure. If a command fails partway through, stop, inspect the counts, and do not blindly rerun the whole sequence.

    9. Restoring data or recovering from a mistake

    • Stop making further manual changes and record what happened, when, and which command was run.
    • Do not immediately import an old SQL export over the live database. A restore can overwrite newer orders and settings.
    • For a recent accidental change, check Cloudflare D1 Time Travel options and the recovery point before restoring. Restoration is a production operation and should be owner-approved.
    • If using a SQL export, restore only into a separately created/test database first and verify its contents before considering any production recovery.
    • After recovery, verify menu, orders, unpaid online orders, daily reports, receipt counter, and customer ordering before resuming normal use.

    Do not use the old “delete all test sales” reset procedure on a live business database. Once real transactions begin, historical sales and daily reports must be retained.

    10. Live-operation checklist

    • Confirm the production D1 database name and ID in wrangler.toml.
    • Confirm owner login works and the owner password is strong and private.
    • Keep ADMIN_PASSWORD and SESSION_SECRET in Cloudflare Worker secrets. Never paste them into source code, SQL, screenshots, or GitHub.
    • Confirm the Worker is deployed and the POS Settings health check reports Cloud API and database as connected.
    • Confirm the customer ordering setting is intentionally enabled or disabled before sharing the public order page.
    • Test a small POS cash sale, a non-cash sale if supported, and an online cash-on-delivery/pickup order flow using clearly identified test data before opening to customers.
    • Verify that unpaid online orders are not treated as completed/paid sales, and that the cashier marks payment only after receiving it.
    • Verify that menu updates appear on the other cashier device and customer ordering page.
    • Make and securely retain a full remote SQL export before the first live day, and repeat backups before migrations or risky maintenance.
    • Keep a simple record of each production migration, Worker deployment, backup filename, date, and person who approved it.
